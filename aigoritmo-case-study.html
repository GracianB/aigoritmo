04 · Diseño de API

Un endpoint, dos capas de lectura

El motor de tarot se expone como endpoint explícito y, además, como acción automática dentro del chat cuando ARCANA detecta intención — sin botones innecesarios.

POST /api/tarot/reading — request
{
  "conversation_id": "uuid",
  "question": "¿Qué debo saber
   sobre mi futuro profesional?",
  "spread_type": "three_card"
}
POST /api/tarot/reading — response
{
  "reading_id": "uuid",
  "cards": [
    { "position": "Pasado",
      "card": "The Hermit" },
    { "position": "Presente",
      "card": "The Magician" },
    { "position": "Futuro",
      "card": "The Star" }
  ],
  "interpretation": "..."
}
05 · Por qué lo comparto

Lo que este proyecto demuestra

Estructurar la ambigüedad

Partir de una idea abierta y convertirla en capas, endpoints y sprints concretos, sin perder de vista qué es negociable y qué no.

Priorizar con criterio

Secuenciar el trabajo (backend → core → avatar → tarot → visión → pulido) para que cada entrega reduzca riesgo antes de sumar complejidad.

Pensar en quien lo va a ver

Los escenarios de demo existen para que la presentación fluya sin improvisar delante de negocio o RRHH.

Cuidar el detalle técnico

De la arquitectura de carpetas al diseño de API, cada decisión evita deuda técnica temprana en lugar de acumularla.
